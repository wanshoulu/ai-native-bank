# Finance Guardrail 隔离增强设计

日期：2026-09-02（2026-09-06 更新）  
状态：已接入 AI 原生手机银行输入 Rail  
范围：文本输入护栏、用户意图智能体及业务执行门禁的协同契约

## 1. 目标

在保持第三方 `upstream/` 源码只读的前提下，修正已验证的明显安全错误，使隔离实验能够可靠区分：

1. 请求允许通过；
2. 请求或回答因安全风险被拦截；
3. 护栏依赖或回答模型不可用，当前请求无法安全完成。

本轮不把第三方项目复制进正式产品，不修改 AI Harbor 其他应用，不建设“智能体行动”护栏，也不替代后续基于 openJiuwen 的正式 Rail/Hook。

## 2. 已确认的问题

当前固定八节点 LangGraph 工作流已经可以运行，但存在以下需要优先修正的问题：

- 输入内容分类器异常时默认放行；
- 输出内容分类器异常时默认放行；
- LLM 安全检测调用异常或输出不是合法契约时默认放行；
- 回答模型异常时返回普通回答形态，并标记 `is_blocked=false`；
- 工作流顶层异常时同样标记 `is_blocked=false`；
- 白名单命中后跳过输入 PII、规则、向量分类和 LLM 安全检查；
- 使用宽泛 `pii` 实体组时，`DATE_TIME`、`LOCATION` 等造成明显误杀；
- PII 依赖可能在运行时尝试联网刷新公共域名数据；
- 拦截话术会暴露内部风险等级、规则或检测细节，且系统故障与用户违规没有清晰区分。

## 3. 方案选择

采用“隔离增强适配层”方案：

- `upstream/` 保持原始固定版本和干净工作树；
- 在 `adapters/` 中增加启动引导、运行时装配、安全结果模型、策略和应答模板；
- 容器启动时先安装增强适配，再加载上游 FastAPI 应用；
- 上游仍负责原有工作流和管理界面，增强层只修复隔离实验的安全语义与明显缺陷；
- 所有增强均有独立测试，便于和原生行为对照，也便于未来迁移到 openJiuwen。

不采用以下方案：

- 直接修改第三方源码：不利于来源审计、升级对比和许可证边界控制；
- 立即重写为 openJiuwen Rail：长期方向正确，但会把本轮“修正原型明显问题”扩大成正式集成项目。

## 4. 运行结构

```text
HTTP /chat
   │
   ▼
隔离增强启动器
   ├─ 装配高敏 PII 策略
   ├─ 禁用全链路白名单旁路
   ├─ 包装内容分类器
   ├─ 包装 LLM 安全检测
   ├─ 包装回答模型和顶层处理
   └─ 统一安全结果与用户话术
   │
   ▼
第三方八节点 LangGraph 工作流（保持只读）
   │
   ▼
AI Harbor 模型与 Embedding 网关
```

增强层不根据转账、余额等银行业务名称编写规则。它只处理通用的安全检测结果、依赖状态、PII 类型和用户应答，因此不会形成针对单一业务场景的硬编码规则引擎。

## 5. 统一决策模型

内部使用四态决策，不再用单个 `is_blocked` 混合表达所有情况：

| 决策 | 含义 | HTTP 兼容表示 | 是否继续生成或返回原回答 |
| --- | --- | --- | --- |
| `allow` | 所有必需检测已通过 | `is_blocked=false` | 是 |
| `review` | 已识别风险语义，但行为目的或必要上下文不足 | `is_blocked=true`、`detected_by=guardrail_review` | 否，只允许安全澄清 |
| `block` | 已确认存在安全风险 | `is_blocked=true` | 否 |
| `unavailable` | 必需检测器或回答模型不可用 | `is_blocked=true`、`detected_by=system_guardrail` | 否 |

`unavailable` 是兼容上游 `ChatResponse` 的保守映射，不代表用户具有攻击行为。内部必须保留独立 `reason_code`，日志和后续 openJiuwen 集成不得把它计入攻击命中率。

首批稳定原因码：

- `unsafe_content`
- `prompt_injection`
- `sensitive_input`
- `sensitive_output`
- `ambiguous_risk_intent`
- `conflicting_safety_evidence`
- `insufficient_safety_context`
- `security_detector_unavailable`
- `answer_model_unavailable`
- `guardrail_runtime_error`

对外响应不返回模型异常、规则表达式、内部分类分数、风险等级、堆栈或原始敏感文本。

### 5.1 语义证据契约

短文本可能因长度不足而跳过 Embedding 分类，但不能因此把 LLM 的所有 `review` 一律降级为 `allow`。安全 LLM 必须同时提交 `semantic_role`：

| `semantic_role` | 含义 | 允许的安全决策 |
| --- | --- | --- |
| `unrelated_or_benign` | 完整短语无安全风险语义，包括无关、口语、无意义或普通负面表达 | `allow` |
| `legitimate_safety_context` | 防范、教育、举报、合规或官方流程语境 | `allow` |
| `underspecified_risk_topic` | 完整短语按自然分词已构成风险主题或通行委婉表达，但没有合法目的或有害目标 | `review` |
| `prohibited_objective` | 请求实施、获取、制作、传播、隐匿或协助有害行为 | `block` |

判定以完整短语和最自然的中文分词为单位，不把相邻汉字机械拼成风险词。确定性的高置信规则只处理攻击、敏感实体、明确有害目标和明确安全的字面状态；其余语义由 LLM 与分类证据共同仲裁。这样扩展的是风险语义类型，而不是逐条追加用户 badcase。

### 5.2 护栏与意图协同矩阵

| 输入 Rail | 意图结果 | 系统动作 |
| --- | --- | --- |
| `allow` | 业务意图 | 允许提交安全状态并进入 A2A/业务规划 |
| `allow` | 非业务或闲聊 | 返回通用非业务承接，不进入业务执行 |
| `review` | 任意 | 回滚推测状态，只签发澄清许可，返回 `clarification_required` |
| `block` | 任意 | 回滚推测状态并返回安全拒绝，不签发执行许可 |
| `unavailable` | 任意 | 回滚推测状态并返回技术不可用，不归因于用户违规 |

意图智能体不能覆盖输入 Rail 的判决，输入 Rail 也不负责把安全的非业务文本强行映射成银行业务。

## 6. 故障策略

### 6.1 必需安全检测器

输入内容分类、LLM 安全检测和输出内容分类属于必需检查。发生超时、连接错误、解析错误或契约不合法时：

1. 终止本次链路；
2. 返回 `unavailable`；
3. 记录结构化原因码和检测阶段；
4. 不返回未经完整检查的模型回答。

这是一种“安全失败关闭”，但用户话术必须表述为服务暂不可用，不能误称用户请求违规。

### 6.4 安全澄清话术

`review` 的安全判决与澄清文案生成是两个不同权限层级：

1. Rail 的 `review` 决定本次不得执行业务；
2. 用户智能体可以生成更自然的澄清文案，但只有澄清权限；
3. 文案模型超时、返回空值或违反结构化契约时，平台使用稳定模板返回 `clarification_required`；
4. 文案生成失败不得改写成 `unavailable`，也不得升级成 `block`；
5. 无论使用模型文案还是平台兜底，推测会话状态都必须回滚，A2A 与业务智能体不得启动。

### 6.2 回答模型

回答模型异常时返回 `answer_model_unavailable`，不再生成 `is_blocked=false` 的伪成功结果。已经完成的护栏判断可以进入内部 Trace，但不向用户暴露。

### 6.3 顶层异常

未被节点包装器处理的异常统一归一化为 `guardrail_runtime_error`。响应内容固定、可重试且不包含异常文本。

## 7. 白名单策略

本轮隔离增强模式下禁用“命中白名单后直接跳到回答模型”的旁路能力。

白名单未来只能用于减少某一类低风险规则的误报，不能绕过：

- 高敏 PII 输入检查；
- LLM 提示词攻击检查；
- 模型输出内容检查；
- 高敏 PII 输出检查。

由于上游白名单只有“全链路跳过”语义，本轮直接加载空白名单。后续在正式 openJiuwen Rail 中再设计带 `scope`、`expiry`、`owner` 和审计记录的局部例外策略。

## 8. PII 策略

PII 不再使用包含日期、地点、普通人名和 URL 的宽泛 `pii` 聚合组。文本问答首批仅检测金融高敏实体：

- `CN_ID_CARD`
- `CN_BANK_CARD`
- `CN_PHONE`
- `PHONE_NUMBER`
- `EMAIL_ADDRESS`
- `CREDIT_CARD`
- `IBAN_CODE`
- `US_BANK_NUMBER`
- `US_SSN`

输入侧默认拦截并提示用户脱敏后重试；输出侧默认拦截，避免模型泄露高敏信息。`DATE_TIME`、`LOCATION`、`PERSON`、`URL`、`DOMAIN_NAME` 不进入首批阻断列表。

运行时必须使用随镜像固定的离线公共域名数据，不允许启动或请求过程中访问公网刷新域名列表。

## 9. 用户应答策略

应答由 `reason_code` 映射到稳定模板，不拼接内部检测细节：

| 场景 | 用户应答原则 |
| --- | --- |
| 诈骗、违法或明显有害内容 | 明确无法协助，并可提示合规、安全的替代方向 |
| 提示词攻击或索取内部策略 | 不泄露内部提示词、规则或系统配置，提示用户重新描述正常金融问题 |
| 输入包含高敏信息 | 提醒遮盖完整卡号、证件号、手机号等后重新提问 |
| 输出检测到高敏信息 | 不展示原回答，提示当前回答因敏感信息保护未能提供 |
| 安全检测器不可用 | 提示安全检查暂时不可用，请稍后重试 |
| 回答模型不可用 | 提示智能服务暂时不可用，请稍后重试 |

同一原因码的 HTTP 与后续 Hook 返回应复用同一模板注册表，避免各入口自行拼话术。

## 10. 测试设计

所有实现按 TDD 完成，至少覆盖：

1. 内容分类器输入异常时进入 `unavailable`，不得放行；
2. 内容分类器输出异常时不返回未经检查的回答；
3. LLM 安全检测异常和非法 JSON 均进入 `unavailable`；
4. 回答模型异常不再返回伪成功；
5. 顶层异常不暴露异常详情；
6. 白名单规则即使存在，也不能绕过必需检查；
7. 日期、地点、普通姓名不再触发高敏 PII 阻断；
8. 合成身份证号、银行卡号、手机号和邮箱仍能阻断；
9. 每类原因码返回稳定、无内部细节的应答；
10. 原有 36 个支持判定样例不得回归；
11. 容器内完整 `/chat` 链路可使用 AI Harbor 模型和 Embedding；
12. 运行期间不会发起公共域名数据刷新请求。

测试只使用显式合成数据，不使用真实客户、账户、会话或业务 Trace。

## 11. 验收标准

- 五个已确认的 fail-open 故障注入用例全部改为安全终止；
- 安全检测失败与用户风险拦截可以在内部结果中明确区分；
- `DATE_TIME`、`LOCATION` 导致的已知误杀归零；
- 高敏 PII 合成样例继续全部命中；
- 白名单不能绕过必需检查；
- 用户话术不包含内部规则、分类分数、风险等级、异常堆栈或敏感原文；
- 上游固定版本目录没有任何修改；
- AI Harbor 与手机银行现有运行服务不受影响；
- 隔离容器停止后不遗留公网端口或长期运行实例。

## 12. 后续迁移边界

本轮可复用到 openJiuwen 的资产仅包括：

- 三态安全决策及原因码；
- PII 策略配置；
- 应答模板注册表；
- 故障语义与测试数据集；
- 工作流闭环评测方法。

第三方 LangGraph 运行结构和第三方源码不进入正式用户智能体。正式接入时，将上述通用资产实现为用户智能体的文本问答 Rail/Hook；未来“智能体行动”护栏则在业务智能体侧单独设计。
