## 结论

第一阶段“文本问答护栏功能闭环”在当前合成测试范围内通过。完整链路已覆盖输入检查、四态裁决、回答生成、输出复检、安全投影、会话 checkpoint、非流式与流式 HTTP。

该结论不等于生产就绪。上游原生实现仍有 fail-open、测试顺序依赖、许可与管理面风险；这些问题由隔离适配层暂时关闭或记录，尚未迁入 openJiuwen。

### 回归集

为规避本机 Docker Desktop 长跑时两次 Linux 后端退出，36 个案例按 12 个一批执行，每批两轮并重建隔离容器。三批结果均为 24/24：

- 合计决策：`allow 24 / block 42 / review 6`；
- 误放 0、误封 0、`review` 不支持 0、`unavailable` 0、错误 0、不稳定案例 0；
- 三批 P95 分别为 6.61 秒、6.42 秒、10.00 秒。

### 盲测集与标签审定

首次盲测为 34/36。唯一失败案例明确询问“应确认哪些合规要求”，原标签却标为 `review`，与已批准策略“明确询问如何合规应放行”冲突。没有修改模型去迎合错误标签，而是留下审定记录并将标签改为 `allow`。

随后发现上游默认 `LLM_TEMPERATURE=0.7` 会令同一边界在 `allow/review` 间波动。隔离启动适配器将温度固定为 `0` 后：

- 关键边界三轮验证 18/18；
- 审定后盲测两批各 18/18，合计 36/36；
- 合计决策：`allow 14 / block 18 / review 4`；
- 误放、误封、错误和不稳定案例均为 0。

## 已闭环的安全行为

1. 输出契约为 `allow / block / review / unavailable`，不再把依赖失败伪装为安全放行。
2. 输入或输出分类器异常、LLM 安全模型异常、非法安全契约、回答模型异常和顶层工作流异常均 fail-closed。
3. 模糊双用途请求进入 `review`；明确询问官方规则或合规要求且未请求规避方法时保持 `allow`。
4. 输入高敏 PII 在回答生成前终止；输出回答必须经过内容与 PII 复检后才可返回。
5. 回答模型若生成完整敏感标识，先低温重生成；第二版仍含敏感标识时丢弃草稿并返回固定非敏感说明。
6. PII 清单收窄到金融高敏实体；无效 Luhn 数字不会被误判为银行卡；有效中国身份证使用校验位确定性识别。
7. 用户可见结果和流式终态不包含内部规则、分类分数、异常堆栈或原始敏感文本。
8. 白名单旁路被禁用，运行时不能关闭必要输入/输出检查。

## 外部追踪与密钥边界

审计发现 Guardrails Hub 默认开启匿名 metrics，并尝试向外部 AWS OTLP 端点发送 span。隔离启动层现已：

- 在导入上游 validator 前关闭 Guardrails metrics 与 remote inferencing；
- 剥离继承的 `OTEL_*`、`LANGSMITH_*`、`LANGCHAIN_*` 端点和密钥；
- 显式设置 `OTEL_SDK_DISABLED=true`；
- Chat 与 Embedding 只使用 AI Harbor 内部服务令牌和网关。

重建后执行 6 个真实案例，运行日志中外部 telemetry/exporter 尝试为 0。

## 上游原生基线说明

上游目录未修改，提交哈希固定且 `git status --porcelain` 为空。原生测试当前结果为 9 passed、2 skipped、1 failed。

失败用例存在上游自身缺陷：PII detector 先按优先级排序实体，随后又用 `set` 遍历；当 18 位数字同时匹配身份证和银行卡正则时，结果依赖 hash/遍历顺序。测试样例 `110101199001011234` 的正确校验位应为 `7`，实际为 `4`，却要求识别为身份证。该用例单独运行通过，整套运行稳定选成银行卡。

本次不修改第三方源码；加固适配层用严格中国身份证校验和银行卡 Luhn 校验避免继承该缺陷。
